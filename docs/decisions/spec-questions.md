## A. โครงสร้างข้อมูล (Data Model)

**1. Multi-tenant?** รองรับหลายตลาด/หลายเจ้าของบน platform เดียวไหม
- ⭐ a) Multi-tenant SaaS (หลายตลาด/หลายเจ้าของ) — เผื่อขายต่อ
- b) ตลาดเดียวก่อน (single-tenant)

**2. Entity หน่วยเช่า** ตลาด(ล็อก) กับ คอนโด(ห้อง) เก็บยังไง
- ⭐ a) Collection เดียว `Unit` มี field `type = market_lock | condo_room`
- b) แยก collection ตลาด vs คอนโด

**3. ลำดับชั้นพื้นที่**
- ⭐ a) ตลาด/อาคาร → โซน → ล็อก (3 ระดับ)
- b) ตลาด → ล็อก (2 ระดับ)
- c) tree ปรับได้ไม่จำกัดชั้น

**4. มิเตอร์ต่อ 1 ล็อก**
- ⭐ a) กำหนดต่อล็อกได้ (บางล็อกไฟอย่างเดียว / บางล็อกไฟ+น้ำ)
- b) ทุกล็อกมีไฟ+น้ำเหมือนกันหมด

**5. ระบบไฟ**
- ⭐ a) รองรับทั้ง 1 เฟส และ 3 เฟส (มี field phase)
- b) 1 เฟสพอ (ตลาดทั่วไป)

## B. โปรโตคอลระดับ Mesh

**6. Mesh implementation**
- ⭐ a) ESP-NOW + routing เอง (เบา คุมเอง latency ต่ำ)
- b) painlessMesh (ตั้งง่าย)
- c) ESP-WIFI-MESH (ทางการ Espressif หนักกว่า)

**7. รูปแบบ packet บน mesh**
- ⭐ a) binary struct (เล็ก/เร็ว ประหยัด airtime)
- b) MessagePack
- c) JSON (อ่านง่ายแต่ใหญ่)

**8. ขนาด UUID ใน packet**
- ⭐ a) short id 4–8 ไบต์ ใน mesh แล้ว map เป็น UUID เต็มที่ server (ประหยัด)
- b) UUIDv4 เต็ม 16 ไบต์ยิงไปเลย

**9. โมเดลส่ง telemetry**
- ⭐ a) node push ทุก 1 นาที (ตามสเปก)
- b) push เมื่อค่าเปลี่ยนเกิน threshold + heartbeat
- c) server poll ขอเป็นครั้งๆ

**10. คำสั่งควบคุม relay (ตัด-ต่อ น้ำ/ไฟ)**
- ⭐ a) ต้องมี ACK + retry 3 ครั้ง (timeout 2 วิ) — กันคำสั่งหาย
- b) ACK ครั้งเดียว
- c) fire-and-forget (ไม่แนะนำ)

## C. โปรโตคอลระดับ Server / Gateway

**11. Gateway (node ใหญ่) ↔ Server เชื่อมด้วย**
- ⭐ a) MQTT (broker) — เหมาะ IoT, pub/sub, reconnect ดี
- b) WebSocket ตรง
- c) HTTP REST (gateway poll)
- d) gRPC

**12. ถ้าใช้ MQTT — broker**
- ⭐ a) self-host (Mosquitto/EMQX ใน Docker)
- b) cloud broker (เสียรายเดือน)

**13. Gateway uplink ออกเน็ต**
- ⭐ a) เลือกได้ต่อไซต์ (4G / WiFi / LAN)
- b) fix 4G
- c) fix WiFi

**14. hardware ตลาด vs คอนโด format ต่างกัน — จัดการยังไง**
- ⭐ a) แยก schema ต่อ device type + มี field `fw_version` / `format_version`
- b) แปลงเป็น format กลางตั้งแต่ที่ gateway ก่อนส่ง server

## D. จัดเก็บข้อมูล & ความปลอดภัย

**15. Retention (ข้อมูลดิบ 1 นาที)**
- ⭐ a) เก็บดิบ 30 วัน แล้ว rollup เป็นรายชั่วโมง/รายวัน (ประหยัดพื้นที่)
- b) เก็บดิบทั้งหมดตลอด
- c) เก็บเฉพาะ rollup (ทิ้งดิบเร็ว)

**16. เก็บ time-series ที่ไหน**
- ⭐ a) MongoDB Time-Series Collection
- b) MongoDB collection ปกติ
- c) แยก TSDB (เช่น InfluxDB/Timescale)

**17. ความปลอดภัยบน mesh**
- ⭐ a) เข้ารหัส payload (AES key ต่อตลาด) + นับ sequence กัน replay
- b) เซ็น HMAC อย่างเดียว
- c) ไม่เข้ารหัส (เครือข่ายปิด)

## E. บิล & เรทราคา

**18. โครงสร้างเรทค่าน้ำ/ไฟ**
- ⭐ a) กำหนดต่อล็อกได้ (default ตกทอดจากโซน/ตลาด)
- b) เรทเดียวทั้งตลาด
- c) ขั้นบันได (tiered ตามหน่วย)

**19. รายการในบิล**
- ⭐ a) แยกบรรทัด (ค่าไฟ / ค่าน้ำ / ค่าเช่า / ค่าจอดรถ / ค่าบริการ)
- b) รวมเป็นยอดเดียว

**20. รอบบิล (วันออกบิล)**
- ⭐ a) กำหนดวัน/เดือน ต่อตลาด (ทุกล็อกใช้รอบเดียวกัน)
- b) กำหนดต่อล็อกต่างกันได้

**21. Prepaid หรือ Postpaid**
- ⭐ a) Postpaid (ใช้ก่อน–ออกบิลรายเดือน)
- b) Prepaid (เติมเครดิตก่อนใช้ หมดตัด auto)
- c) รองรับทั้งคู่

**22. ค่าปรับจ่ายช้า**
- ⭐ a) % ของยอดค้าง
- b) จำนวนคงที่/ครั้ง
- c) คิดต่อวัน
- d) ไม่มีค่าปรับ

**23. ตรวจสลิปการจ่าย**
- ⭐ a) ผู้เช่าแนบรูปสลิป → เจ้าของกดยืนยันเอง (manual)
- b) อ่าน QR สลิปอัตโนมัติ
- c) เชื่อม API ธนาคาร (ยุ่งกว่า แต่ auto จริง)

## F. การควบคุม & การตัดน้ำไฟ

**24. ตัดอัตโนมัติหลังครบกำหนดจ่าย (ผ่อนผัน)**
- ⭐ a) กำหนดจำนวนวันเองต่อตลาด
- b) 3 วัน
- c) 7 วัน

**25. เมื่อค้างจ่าย จะตัดอะไร**
- ⭐ a) เจ้าของเลือกต่อครั้ง (ไฟ / น้ำ / ทั้งคู่)
- b) ตัดไฟก่อน (น้ำไม่ตัด)
- c) ตัดทั้งน้ำ+ไฟ

**26. Override (เจ้าของเปิดใช้ทั้งที่ยังค้าง)**
- ⭐ a) บันทึก log + เหตุผล + วันหมดอายุ override
- b) เปิดเฉยๆ ไม่ต้องบันทึก

**27. กดตัด/ต่อ แบบ manual**
- ⭐ a) ต้องยืนยัน 2 ชั้น (พิมพ์ยืนยัน / OTP) กันกดพลาด
- b) กดครั้งเดียวทำเลย
